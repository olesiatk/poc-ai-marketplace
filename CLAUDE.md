# Project rules

- All code must be in English: source code, comments, identifiers, UI copy/strings, commit messages, and any data files (`public/data/*.json`). Do not introduce non-English text anywhere in the repo, even though this is a POC for a Ukrainian-market product.

# Stack & architecture

- Angular 22: standalone components, zoneless (no zone.js), signals for all state (`signal`/`computed`/`effect`), and the new `@if`/`@for`/`@switch` control-flow syntax — not NgModules, not `*ngIf`/`*ngFor`, not `provideZoneChangeDetection`.
- The app shows exactly one catalog per build, chosen by `ACTIVE_DATASET` in `src/app/datasets/active.ts` (currently Beauty). Everything catalog-specific — data file paths (products, reviews, embeddings, AI snapshots), the LLM prompt's domain wording and examples, the local search's concept groups (synonyms), the preset queries (chips) and where their recorded AI results live, search placeholder, and the guided tour's demo query — lives in that catalog's config (`src/app/datasets/beauty.ts`, `health.ts`); the rest of the app is catalog-agnostic and must stay that way, so switching catalogs is a one-line change. Concept-group terms only ever match text that contains them verbatim, so pick them from wording that actually recurs in that catalog. `demoQuery` should give the top result both an exact and a synonym highlight — re-check it after changing a catalog or its concept groups.
- A search shows a side-by-side comparison (`SearchComparisonComponent`): left = keyword search = `localHeuristicSearch(query, …, [])` (same stemming + field weights, NO concept groups, no LLM — keep it an honest baseline, never a deliberately weakened one); right = AI search via `AiResults` (`src/app/lib/ai-results.ts`). Both sides share the manual filters; each paginates on its own. Results are horizontal tiles (`ProductRowComponent`); tiles per row and page sizes come from one breakpoint table in the component (`lib/breakpoints.ts`), like the browse grid — don't add parallel CSS breakpoints. No query = the plain browse grid.
- `AiResults` serves preset queries from `public/data/<name>-ai-snapshots.json` (real LLM runs recorded by `npm run record:ai -- <beauty|health>`, paced ~1 min per preset to fit a tight per-minute token limit) so the page-load comparison and chips never touch the LLM and every visitor sees the same thing. Other queries go live, cached per session, paced by a client-side model of the deployment's per-minute token budget in `AiResults` (a token bucket of `AI_TOKENS_PER_MINUTE`, baked in at build time via `environment.ts`; one search reserves ~4.8K): a query typed while the budget is short shows "AI will search in N s…" and runs live when there's room — only the latest query, if it was replaced meanwhile (an LLM failure still falls back to local synonym search, labeled "AI busy"). If the server has no AI configured (`/api/chat` answers 503), live search is switched off for the session and the AI side shows local synonym search without the "busy" label. The search button is never disabled while searching — that would also block Enter, so an edited query couldn’t replace the running one. Re-record after changing presets, the catalog, the prompts or the model deployment.
- A query can set filters by itself (`lib/query-filters.ts`, deterministic like `lib/price-query.ts`): a price ("under $25") moves the slider wherever it appears, but categories and item forms only when the query names them explicitly next to "category"/"form" — "cream form", "form: cream or liquid", "category hair care", "skin care category" — never from an everyday product word ("a hydrating cream" filters nothing). Several values can be listed; the category and item form filters are multi-select. `App` tracks which filters came from the query (tagged "from your query" in the filters bar) and puts them back when the next query doesn't name them; a filter changed by hand is left alone. Item forms come from the marketplace's "Item Form" detail, or the title when a product states none (`lib/catalog.ts`). These filters apply to both comparison sides, like any manual filter.
- Search matches on word stems (`lib/stem.ts`, a deliberately light stemmer) on both sides — word forms ("frizzy"/"frizz") are the baseline's job too; only real synonyms/intent should separate the two sides.
- `public/data/{health,beauty}-products.json` / `{health,beauty}-reviews.json` are static data, a one-off extract from the Amazon Reviews 2023 "All Beauty" / "Health & Personal Care" dumps (the raw dumps and the extraction script are gone, so nothing regenerates them). Invariants the app relies on: every product has a MAIN photo as `images[0]`, a title, description, price, features and at least one review; every review's `productId` exists; `category` is our own subcategory (the raw data had none). If you edit them by hand, keep those invariants and ids consistent, rerun `npm run eval:search`, and re-record AI snapshots (`npm run record:ai -- <name> --all`).
- LLM and secrets: AI search uses Azure OpenAI (a model deployment in Azure AI Foundry, `gpt-4.1-mini` by default). The browser never holds the key: `src/app/lib/llm-client.ts` posts `{system, user, maxTokens}` to the app's own `/api/chat`, served in production by the Azure Static Web App's managed function (`api/src/functions/chat.js`) and locally by `scripts/dev-api.mjs` (started by `npm start`; `ng serve` proxies `/api` to it via `proxy.conf.json`). Both wrap the same framework-free handler, `api/src/openai.js`, which reads `AZURE_OPENAI_ENDPOINT`/`AZURE_OPENAI_API_KEY`/`AZURE_OPENAI_DEPLOYMENT` (SWA environment variables in Azure, `.env` locally), calls the OpenAI-compatible v1 endpoint (`<endpoint>/openai/v1/chat/completions`, deployment name as `model`), and only accepts requests shaped like the app's two calls (size and `maxTokens` caps) — keep those caps in line if the prompts grow. Node scripts call Azure directly through the same module (`scripts/direct-ai.ts` swaps the transport). Never put the key in the frontend build, `environment.ts` or a CI variable that reaches the build. `src/environments/environment.ts` holds only build-time, non-secret settings; it's generated from `.env`/the process environment by `scripts/set-env.js` via npm's `prestart`/`prebuild` hooks and gitignored — never hand-edit or commit it; use `npm start`/`npm run build` (not bare `ng serve`/`ng build`) as entry points so it's always regenerated.
- AI search pipeline (`src/app/lib/ai-search.ts`): the full product catalog (1000+ items) is far too large to send to the LLM in one request — slow, costly and past typical per-minute token limits (the provider counts the prompt PLUS the whole `max_tokens` reservation) — so an AI search is two LLM calls: a small "plan" call (query + category list → which categories to look in and which words a fitting product would use) and a "rerank" call over at most `MAX_CANDIDATES` (32) products picked locally (`lib/candidates.ts`: keyword search's first page from any category, then two rankings fused by position — `localHeuristicSearch` within the planned categories with the plan's terms as extra synonyms, and vector search — cut off where scores fall away, no padding past `MIN_CANDIDATES`). Vector search (`lib/vector-search.ts`): every product is embedded ahead of time with a small model (`Xenova/all-MiniLM-L6-v2`, int8, `npm run embed:catalog -- <name>` → `public/data/<name>-embeddings.json`; re-run after changing the catalog or `embeddingText()`); the query is embedded at search time by transformers.js — in the browser it lazy-loads its runtime and the ~23 MB model (from Hugging Face and jsDelivr) the first time the search box gets focus, in Node for the scripts. The model is too small to reason, so the query is embedded together with the AI plan's words. After the rerank the AI column continues with up to `TAIL_MAX` more products found by meaning (`bySimilarity`, "similar in meaning" on the tile), but only those at least as close as the closest quarter of the matches the model accepted — raw similarity alone puts junk and good matches in the same range. A failed model/embeddings load just leaves vector search out. The catalog goes as numbered plain lines under `## Category` headers (not JSON; the model answers with line numbers, mapped back in code); only the top `RICH_CANDIDATES` carry features/description/query-relevant review excerpts, all truncated (`MAX_*_CHARS`). `max_tokens` is kept at ~2-3x the longest real answers (plan 300, rerank 900). Plan + rerank together come to ~4.5K tokens — don't revert to sending the whole catalog or untruncated text, and re-measure before raising those limits (and `LIVE_SEARCH_TOKENS` plus the `/api` caps with them); a 413 means the payload grew too large. JSON mode (`response_format: json_object`), not strict structured outputs — `parseMatches` recovers answers strict mode would reject. A failed plan call isn't fatal: retrieval falls back to the concept groups over the whole catalog. A 429 is the deployment's per-minute limit — the app falls back to local search either way. If calls start failing with a 404/`DeploymentNotFound`, the deployment name in `AZURE_OPENAI_DEPLOYMENT` doesn't match the one in Foundry (or the model version was retired there).
- Picking preset queries: `npm run report:presets -- <beauty|health>` scores each preset (from its recording) on what makes a convincing demo — more AI results than keyword ones, a keyword first page that's mostly "Filtered out by AI", many "Found only by AI", two+ categories/forms from the query; whether AI's picks actually fit better is judged by eye with `--detail`. Screen candidate queries for free with `--screen "query" …` (keyword side only), then run the best few live with `--try "query" …` (one live AI search each, nothing recorded).
- Deployment: GitLab CI (`.gitlab-ci.yml`) tests every push and deploys the default branch to the Azure Static Web App `poc-marketplace-search-frontend` with the SWA CLI (site = `dist/poc-marketplace-search/browser`, managed API = `api/`, runtime from `public/staticwebapp.config.json`). Azure resources live in the `poc-marketplace-search-rg` resource group and are named `poc-marketplace-search-<resource>`. See README.md for the setup steps.
- Tests: `npm test` runs unit specs (vitest via `@angular/build:unit-test`). `npm run eval:search` is a retrieval-accuracy regression check for the synonym-expansion search, with hand-picked ground-truth ids from the Beauty catalog (it always evaluates Beauty, whichever catalog is active) — if that catalog is rebuilt or its concept groups change meaningfully, rerun it and re-pick ground-truth ids if it fails.
- When changing UI, verify against an actual running instance (dev server + a headless-browser screenshot + console-error check) — a passing build/test suite alone doesn't confirm the UI actually looks or behaves right.
- The guided tour (`src/app/lib/tour.ts`, `driver.js`) is owned by `App`, not by a leaf component — its last few steps run a live demo (fills the search box, runs a real search, opens a card) and need App-level state (`onSearch`, `filteredProducts`, `selectedId`). A step with a custom `popover.onNextClick` must call `opts.driver.moveNext()` itself — providing that hook fully replaces the default advance behavior. Cleanup (clearing the demo query, closing the modal) lives in the driver `Config`'s `onDestroyStarted`, which fires however the tour ends (Done, the × button, Escape, overlay click) — but per driver.js's own internals, that hook only *asks* to destroy; you must call `opts.driver.destroy()` yourself inside it or the tour never actually closes. **`driver.destroy()` called directly (e.g. from outside the tour, like the postMessage bridge's dismiss handler) bypasses `onDestroyStarted` entirely** (its public `destroy` is the "force" path) — so any external code that ends the tour must replicate `App`'s reset logic (`resetTourDemo()`) itself before calling `destroy()`, or the demo state/`poc-tour-status` broadcast never fires.
- This app is designed to be embedded in a host page's `<iframe>` — `src/app/lib/post-message.ts` is a deliberately small subset of a larger shared postMessage contract, hand-picked for what this app actually has (no file upload/media preview, no client-side routing, so those message types were left out). It sends `poc-frame-ready`/`poc-resize-iframe` (wired in `App` via `src/app/lib/iframe-resize.ts`'s `ResizeObserver`), `poc-tour-status` and `poc-scroll-into-view` (from the guided tour), and `poc-modal` (from `ProductModalComponent`'s mount/unmount). It listens for `ask-for-height`, `poc-host-ready`, and `poc-dismiss` (host-forwarded click/Escape on its own dim, for whichever overlay — tour or modal — is currently open; both listen independently, same as native Escape already behaves when both happen to be open at once). All of it is a no-op when the app isn't actually embedded (`isEmbedded()` checks `window.parent !== window`), so it's silent and harmless in normal dev/standalone use.
