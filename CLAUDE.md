# Project rules

- All code must be in English: source code, comments, identifiers, UI copy/strings, commit messages, and any data files (`public/data/*.json`). Do not introduce non-English text anywhere in the repo, even though this is a POC for a Ukrainian-market product.

# Stack & architecture

- Angular 22: standalone components, zoneless (no zone.js), signals for all state (`signal`/`computed`/`effect`), and the new `@if`/`@for`/`@switch` control-flow syntax — not NgModules, not `*ngIf`/`*ngFor`, not `provideZoneChangeDetection`.
- The app shows exactly one catalog per build, chosen by `ACTIVE_DATASET` in `src/app/datasets/active.ts` (currently Beauty). Everything catalog-specific — data file paths, the Groq prompt's domain wording and examples, the local search's concept groups (synonyms), the preset queries (chips) and where their recorded AI results live, search placeholder, and the guided tour's demo query — lives in that catalog's config (`src/app/datasets/beauty.ts`, `health.ts`); the rest of the app is catalog-agnostic and must stay that way, so switching catalogs is a one-line change. Concept-group terms only ever match text that contains them verbatim, so pick them from wording that actually recurs in that catalog. `demoQuery` should give the top result both an exact and a synonym highlight — re-check it after changing a catalog or its concept groups.
- A search shows a side-by-side comparison (`SearchComparisonComponent`): left = keyword search = `localHeuristicSearch(query, …, [])` (same stemming + field weights, NO concept groups, no LLM — keep it an honest baseline, never a deliberately weakened one); right = AI search via `AiResults` (`src/app/lib/ai-results.ts`). Both sides share the manual filters; each paginates on its own. Card vs list layout and page sizes come from one breakpoint table in the component (`lib/breakpoints.ts`), like the browse grid — don't add parallel CSS breakpoints. No query = the plain browse grid.
- `AiResults` serves preset queries from `public/data/<name>-ai-snapshots.json` (real Groq runs recorded by `npm run record:ai -- <beauty|health>`, ~1 min per preset because of the rate limit) so the page-load comparison and chips never touch the LLM — the key is shared by every visitor, so a live call on page load would 429 for everyone after the first. Other queries go live, cached per session, with a 60 s cooldown that falls straight back to local synonym search (labeled "AI busy"). Re-record after changing presets, the catalog, or the Groq prompt/model.
- Search matches on word stems (`lib/stem.ts`, a deliberately light stemmer) on both sides — word forms ("frizzy"/"frizz") are the baseline's job too; only real synonyms/intent should separate the two sides.
- `public/data/products.json`, `reviews.json`, `products-with-reviews.json` and `scripts/generate-catalog.js` are leftovers from the old furniture catalog: kept on disk but unused — nothing in the app, tests, scripts or the build may reference them (`angular.json` excludes them from the build output).
- `public/data/{health,beauty}-products.json` / `{health,beauty}-reviews.json` are static data, a one-off extract from the Amazon Reviews 2023 "All Beauty" / "Health & Personal Care" dumps (the raw dumps and the extraction script are gone, so nothing regenerates them). Invariants the app relies on: every product has a MAIN photo as `images[0]`, a title, description, price, features and at least one review; every review's `productId` exists; `category` is our own subcategory (the raw data had none). If you edit them by hand, keep those invariants and ids consistent, rerun `npm run eval:search`, and re-record AI snapshots (`npm run record:ai -- <name> --all`).
- Secrets: `.env` (gitignored) → `scripts/set-env.js` generates `src/environments/environment.ts` automatically via npm's `prestart`/`prebuild` hooks. `environment.ts` is gitignored too (it ends up holding the real key on disk) — never hand-edit it, hardcode a key there, or force-add/commit it; it's regenerated on every `npm start`/`npm run build`, so a fresh clone gets it back automatically as long as those (not bare `ng build`/`ng serve`) are the entry points.
- Groq's model catalog changes over time — if `aiSearch()` in `src/app/lib/groq.ts` starts failing with a `model_not_found`/404, the configured `GROQ_MODEL` has likely been retired; check `https://console.groq.com/docs/models` (or `GET /openai/v1/models` with the actual key) for what's currently live. Also: the full product catalog (1000+ items) is far too large to send to Groq in one request on typical free-tier rate limits (this project's account: 8K tokens/minute, and Groq counts the prompt PLUS the whole `max_tokens` reservation against it), so `groq.ts` pre-narrows it with `localHeuristicSearch` to `MAX_CANDIDATES` (20) and truncates each entry's title/description/features/reviews (`MAX_*_CHARS`) before ever calling the API — don't revert to sending the whole catalog or untruncated text; a 413 "Request too large" means the payload grew past the limit. For gpt-oss models `groq.ts` sends `reasoning_effort: "low"` — at the default effort the model's reasoning sometimes used up `max_tokens` and Groq rejected the truncated answer with a 400 `json_validate_failed`. A 429 is just the per-minute budget being used up by back-to-back searches — the app falls back to local search either way.
- Tests: `npm test` runs unit specs (vitest via `@angular/build:unit-test`). `npm run eval:search` is a retrieval-accuracy regression check for the synonym-expansion search, with hand-picked ground-truth ids from the Beauty catalog (it always evaluates Beauty, whichever catalog is active) — if that catalog is rebuilt or its concept groups change meaningfully, rerun it and re-pick ground-truth ids if it fails.
- When changing UI, verify against an actual running instance (dev server + a headless-browser screenshot + console-error check) — a passing build/test suite alone doesn't confirm the UI actually looks or behaves right.
- The guided tour (`src/app/lib/tour.ts`, `driver.js`) is owned by `App`, not by a leaf component — its last few steps run a live demo (fills the search box, runs a real search, opens a card) and need App-level state (`onSearch`, `filteredProducts`, `selectedId`). A step with a custom `popover.onNextClick` must call `opts.driver.moveNext()` itself — providing that hook fully replaces the default advance behavior. Cleanup (clearing the demo query, closing the modal) lives in the driver `Config`'s `onDestroyStarted`, which fires however the tour ends (Done, the × button, Escape, overlay click) — but per driver.js's own internals, that hook only *asks* to destroy; you must call `opts.driver.destroy()` yourself inside it or the tour never actually closes. **`driver.destroy()` called directly (e.g. from outside the tour, like the postMessage bridge's dismiss handler) bypasses `onDestroyStarted` entirely** (its public `destroy` is the "force" path) — so any external code that ends the tour must replicate `App`'s reset logic (`resetTourDemo()`) itself before calling `destroy()`, or the demo state/`poc-tour-status` broadcast never fires.
- This app is designed to be embedded in a host page's `<iframe>` — `src/app/lib/post-message.ts` is a deliberately small subset of a larger shared postMessage contract, hand-picked for what this app actually has (no file upload/media preview, no client-side routing, so those message types were left out). It sends `poc-frame-ready`/`poc-resize-iframe` (wired in `App` via `src/app/lib/iframe-resize.ts`'s `ResizeObserver`), `poc-tour-status` and `poc-scroll-into-view` (from the guided tour), and `poc-modal` (from `ProductModalComponent`'s mount/unmount). It listens for `ask-for-height`, `poc-host-ready`, and `poc-dismiss` (host-forwarded click/Escape on its own dim, for whichever overlay — tour or modal — is currently open; both listen independently, same as native Escape already behaves when both happen to be open at once). All of it is a no-op when the app isn't actually embedded (`isEmbedded()` checks `window.parent !== window`), so it's silent and harmless in normal dev/standalone use.
